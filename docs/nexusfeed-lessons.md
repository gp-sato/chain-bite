# NexusFeedから再利用する知見

この文書は、NexusFeedのコミット履歴からChainBiteに再利用する設計判断と失敗事例を抜き出したものです。NexusFeedの仕様をChainBiteへ引き継ぐための文書ではなく、同じ問題を繰り返さないための判断材料として扱います。

ChainBiteの現在の仕様・用語は [CONTEXT.md](../CONTEXT.md) を正史とし、個別の設計判断は [ADR](./adr/) に記録します。

## 1. 再利用するものと持ち込まないもの

| 区分 | 内容 | ChainBiteでの扱い |
| --- | --- | --- |
| 再利用 | HTTPのタイムアウト、限定的なリトライ、URL解決、OGP画像抽出、robots.txtのキャッシュ | `lib/http.ts`、`lib/content.ts`、`lib/robots.ts` に移植済み |
| 再利用 | 公式サイトごとの差分を共通処理から隠すアダプター境界 | `BrandAdapter` → `RawItem` → 共通保存パイプラインとして採用 |
| 再利用 | 検索、無限スクロール、ブックマークなどの閲覧UI | `Item` 向けに移植済み。要件に合わない部分は再実装する |
| 条件付き再利用 | Queueの冪等性キー、条件付きロック、孤立処理の回収 | 初期MVPではQueueを使わない。非同期処理を導入する場合の必須条件とする |
| 持ち込まない | RSS固有の `Source`、`Category`、`NewsItem` モデル | ChainBiteでは `Brand` と `Item` に置き換える |
| 持ち込まない | 初期段階からのVercel Queue、`JobExecution`、複雑な実行ログ基盤 | 実測した運用上の必要性が出るまで導入しない |

## 2. 失敗事例から得たルール

### 2.1 外部取得は必ず時間制限を持つ

NexusFeedでは、外部RSSの取得にタイムアウトがなく、応答しないフィードがCron全体を待たせました。さらに、Queueへの送信も1件がハングするとチャンク全体が完了しない問題がありました（`7cc1994`、`728ca0c`）。

ChainBiteでは次を守ります。

- ブランドごとのHTTPリクエストにタイムアウトを設定する
- リトライは429、408、5xx、タイムアウト、ネットワーク障害など一時的な失敗に限定する
- 404など恒久的な失敗は無駄に再試行しない
- Cronには、プラットフォームの最大実行時間とは別に内部の締切を設ける
- 締切に達した処理は失敗として隠さず、次回実行で再取得できる状態にする

現在の共通HTTP処理は、既定8秒・最大1回のリトライです。ブランド別アダプターと日次Cronを実装するときは、この制限を迂回する直接の `fetch` を追加しないことを原則とします。

### 2.2 1つの情報源の障害で全体を失敗させない

初期のNexusFeedは複数ソースの処理を、1つの失敗が全体へ波及しないよう `Promise.allSettled()` を使う形へ変更しました（`41cd176`）。

ChainBiteでも、あるブランドの公式サイトが停止・仕様変更・レート制限になっても、他ブランドの同期結果は保存できるようにします。同期結果には少なくともブランド単位の成功・失敗を残し、全体成功と個別失敗を混同しません。

### 2.3 DB保存と非同期処理の間には隙間がある

NexusFeedでは、記事をDBへ保存した直後にQueue送信が失敗すると、記事だけが `QUEUED` のまま残り、次回同期では「既存記事」としてスキップされる取りこぼしが発生しました（`ecb7420`）。

ChainBiteの初期MVPはQueueを使わないため、この隙間を先に作りません。将来、画像取得や分類などを非同期化する場合は、次の条件を満たしてから導入します。

- DB内の状態遷移を条件付き更新で行う
- Queue送信の成功・失敗件数と対象IDを呼び出し元へ返す
- 送信成功後に応答を受け取れないケースを想定し、冪等性キーを付ける
- 一定時間 `QUEUED` のまま残ったレコードを回収するSweeperを持つ
- Queueの重複配信を前提に、処理は複数回実行されても壊れないようにする

### 2.4 `PROCESSING` は永続的な状態にしない

Queueの再配信時に、先行処理がクラッシュして `PROCESSING` のまま残ったレコードを後続処理が取得できない問題がありました（`6732a49`）。対策では、同一メッセージの再配信または一定時間を超えた `PROCESSING` を再取得できるようにしました。

したがって、将来非同期処理を追加する場合は、状態だけでなく開始時刻・メッセージ識別子・タイムアウト閾値を設計します。単純な「処理中なら永久にスキップ」は採用しません。

### 2.5 エラーをログだけにして成功扱いにしない

NexusFeedでは、DB保存やQueue投入の失敗をログ出力だけで処理し、Cronが `200 OK` を返してしまうサイレント障害がありました。監視上は成功に見えるため、データが欠落してからしか気付けませんでした（`1c814fc`、`d9c7aab`）。

ChainBiteでは、少なくとも次を区別します。

- 一部ブランドの失敗: 他ブランドの成功は確定し、部分失敗として扱う
- DB保存など共通パイプラインの失敗: 同期全体の失敗として扱う
- 取得対象が0件: 正常な空結果と、全ブランド失敗を区別する

初期MVPでは実行ログテーブルを持たないため、Cronのレスポンス、構造化ログ、テストでこの区別を失わないようにします。

### 2.6 監視用テーブルは有用だが、最初から増やさない

NexusFeedではVercelのログ保存期間が短く、後から障害原因を調べられない問題を受けて、`JobExecution`、フィード別実行結果、イベントログをDBへ保存しました（`d9c7aab`）。一方で、モデル・マイグレーション・クリーンアップ・記録処理が増えました。

ChainBiteの初期MVPでは、Vercelとコンソールのログで運用します。同期対象が増え、失敗原因の追跡にログだけでは足りないと確認できた時点で、必要最小限の実行履歴モデルを追加します。

### 2.7 データ保持期間は後回しにしすぎない

NexusFeedでは、蓄積した古いニュースを削除する専用Cronが後から必要になりました（`642b8f6`）。ChainBiteでも公式情報を蓄積し続けるなら、MVP後に次を決めます。

- 何日分を表示・保持するか
- 期間限定商品の終了後に残すか
- 削除処理を一度に何件まで行うか
- 実行時間の締切と、次回への継続方法

これは現時点では未決定です。保存期間を決めるまでは、削除処理を推測で実装しません。

## 3. ChainBiteへの適用状況

### 適用済み

- `Brand` と `Item` を分離したデータモデル
- `BrandAdapter` と `RawItem` の小さな共通境界
- 8秒のHTTPタイムアウトと限定的なリトライ
- 相対URL解決、OGP/Twitter画像のフォールバック抽出
- オリジン単位・24時間のrobots.txtキャッシュ
- 取得元の生データを `rawPayload` に保持する方針

robots.txtの取得失敗や404は現在Fail Openとして扱っています。これは取得不能時に本体の収集まで止めないための暫定判断であり、対象サイトの利用規約・robots.txtの解釈を確認したうえで見直せます。

### 実装時に引き継ぐこと

- ブランド別アダプターは共通HTTP処理を利用する
- 公式サイトごとのHTML差分はアダプター内に閉じ込める
- `rawPayload` を捨てず、タグ判定ルールを後から再実行できるようにする
- 日次同期ではブランド単位の結果を集計する
- Queueや実行ログテーブルは、必要性を測定してから追加する
